## Development Commands

Standard Vite project — from the project root:

- `npm install` — install dependencies
- `npm run dev` — start the dev server (Vite default port `5173`, auto-increments to the next free port if occupied — check actual bound port before assuming 5173)
- `npm run build` — production build to `dist/`
- `npm run preview` — preview the production build locally
- `npm run lint` — ESLint (flat config, `eslint.config.js`)

No TypeScript (despite `@types/react`/`@types/react-dom` in devDependencies — those are editor-IntelliSense-only), no test suite, no CI configured yet.

**Dev server dies frequently between turns in this tool environment** (background process gets killed when the session/turn boundary resets) — this is routine, not a bug to chase. Expect to restart it often: check `Get-CimInstance Win32_Process -Filter "Name='node.exe'" | Where-Object { $_.CommandLine -like "*sharpable-website*" }` (PowerShell) before assuming it's still running, restart with `npm run dev` in the background if not, confirm the bound port via `Get-NetTCPConnection`, then open/reconnect the browser preview. **After any `tailwind.config.js` color change specifically**, a plain restart isn't always enough either — hard-navigate the browser tab (not just re-check) before trusting computed colors.

**Stale Tailwind/Vite cache gotcha (hit repeatedly in one session, cost real time each time)**: after editing a component to use a **new arbitrary-value class** that didn't exist anywhere in the codebase before (e.g. `pb-[clamp(4.5rem,16vh,8rem)]`, `-mx-[3rem]`), a plain dev-server restart sometimes serves a stale bundle that's missing the new utility entirely — the class sits correctly in the JSX/DOM, but `getComputedStyle` shows browser defaults (e.g. `position: relative` instead of `sticky`, `margin-top: 0px` instead of the intended negative value) as if the class were never generated. This reads exactly like a real positioning bug and is easy to chase down the wrong path. **Fix**: `rm -rf node_modules/.vite` before restarting (`Stop-Process` the node process first, delete the cache dir, then `npm run dev` again) — this forces Tailwind/Vite to fully re-scan and re-bundle rather than reuse a cache that predates the new class. **Always verify** any brand-new arbitrary-value class actually compiled (check `getComputedStyle` in the browser) before concluding a positioning/sizing bug is a real logic error rather than this cache issue — this exact false alarm happened more than once.

**Programmatic scroll doesn't reliably fire native events in this tool's Browser pane** — `window.scrollTo()`/`scrollBy()`/`Element.scrollIntoView()` move the actual scroll position but frequently don't dispatch the `'scroll'` event, don't run `requestAnimationFrame` callbacks reliably, and don't trigger `position: sticky` re-resolution — all things a real user's scroll input does automatically. This makes JS-driven scroll simulation useless for verifying anything scroll-linked (GSAP ScrollTrigger, the Testimonials carousel's wrap logic, ServicesGrid's mobile journey spine, any `position: sticky` element). **What actually works**: a real simulated gesture via the `computer` tool's `scroll` action (max `scroll_amount: 10` per call, batch several via `browser_batch` to cover distance), then `computer{action:"screenshot"}` to confirm visually — or `computer{action:"scroll_to", ref: "..."}` using a ref from `read_page`/`find` to jump to a specific element reliably (far more precise than blind pixel-scrolling or the broken `scrollIntoView`). Also worth knowing: the Browser pane sometimes reports itself as not compositing frames at all (`document.hidden === true`, screenshots time out, `requestAnimationFrame` never fires) for stretches of a session for reasons outside this tool's control — retry later in the same session rather than assuming a fix is needed; when it's confirmed hidden, fall back to direct DOM/computed-style assertions instead of visual checks, and say so explicitly rather than claiming a visual check happened when it didn't. The `computer` tool's own `scroll` action can also silently no-op (reports success, `window.scrollY` never moves) for stretches of a session unrelated to the `document.hidden` issue — if a real gesture doesn't move `scrollY` after a couple of tries, fall back to `window.scrollTo({top, behavior:'instant'})` + a manual `window.dispatchEvent(new Event('scroll'))` (the dispatch is what actually invokes `addEventListener('scroll', ...)` handlers; `scrollTo` alone won't), then wait ~1s for GSAP/`scroll-behavior:smooth` to settle before reading state back.

**This applies to canvas/WebGL animations too, not just scroll-linked CSS** — a `requestAnimationFrame` loop driving a `<canvas>` (e.g. `HeroShaderBackground.jsx`) is just as stuck as everything else while `document.hidden === true`, so a screenshot taken then will show a frozen frame with no live mouse-reactivity even though the code is correct. **A more rigorous check that doesn't depend on rAF or `document.hidden` at all**: grab the same canvas's WebGL context again from outside the component (`canvas.getContext('webgl')` returns the *same* context, not a new one), read back `gl.getParameter(gl.CURRENT_PROGRAM)` to get the already-linked program, look up its uniform locations again by name, force-set them to specific test values, call `gl.drawArrays(...)`, then `gl.readPixels(...)` *immediately* in that same synchronous call — this bypasses the browser's own frame scheduling entirely and proves the shader math is correct (e.g. compare the same pixel with a `uHover` uniform forced to `0` vs `1` and diff the RGB output) even when a live on-screen check is blocked. For verifying a *trail*/*path* effect specifically (not just a single point), simulate a synthetic multi-point path and check that the readback brightness changes *smoothly and monotonically* along it, not just that the endpoints look right — this is what caught the difference between the discrete-blob trail and the continuous-ribbon one during the `HeroShaderBackground` trail work (later reverted; see the `Hero` entry below).

**`read_console_messages` can return a stale/cached error from a *previous* failed HMR update, not the current page state** — hit while iterating on `HeroShaderBackground.jsx`: after fixing a `ReferenceError` (a leftover reference to a since-removed constant), the tool kept reporting the exact same error with the exact same timestamp across multiple fresh navigations and even a full dev-server restart, while the component was actually compiling and running correctly the whole time (confirmed via `gl.getParameter(gl.CURRENT_PROGRAM)` returning a valid linked program with `gl.getError()` returning `0`). **Don't trust a console error at face value if you've since fixed the code it points to** — re-verify via the actual runtime behavior (a WebGL readback, a computed style, a DOM query) rather than assuming the bug is still live just because the log line is still there.

**`window.scrollTo(x, y)` (the legacy 2-argument form) is equivalent to `behavior: 'auto'`, which defers to whatever `scroll-behavior` the target element has** — this project sets `html { scroll-behavior: smooth }` globally (`index.css`), so any "instant jump to a position" call written as the 2-arg form actually *animates* there over a couple hundred ms instead of snapping. This was a real, user-visible bug (legal pages "scrolling up briefly" instead of opening already at the top) that survived an earlier fix that only addressed the *timing* (moving the effect from `useEffect` to `useLayoutEffect`) without addressing this. **Whenever an instant, non-animated scroll position is actually intended, always use the explicit object form with `behavior: 'instant'`** — `window.scrollTo({ top, left, behavior: 'instant' })` — never the bare 2-arg form, anywhere in this codebase.

**React 18 `<StrictMode>` (this project wraps everything in it, `main.jsx`) double-invokes effects in dev** — mount → cleanup → mount again, synchronously, before the user sees anything, specifically to help catch missing-cleanup bugs. This is invisible for most effects, but **an effect that destructively reads-and-clears external state (e.g. `sessionStorage.getItem(...)` immediately followed by `removeItem(...)`) as its first action will have that first, throwaway StrictMode invocation consume the value before the second, real, lasting invocation ever runs** — silently breaking the feature with no error anywhere (hit in `App.jsx`'s scroll-restoration effect; see the legal-pages entry below for the full story). If an effect needs to destructively consume something, defer the read-and-clear until the exact moment the value is actually used/applied (e.g. inside a guarded callback only one invocation can reach), not as the effect's first line.

## High-Level Architecture

- **`src/main.jsx`** — entry point. Wraps everything in `LanguageProvider` (i18n context, see below) then `BrowserRouter` with three routes:
  - `/` → `App` (the entire one-page marketing site)
  - `/privacy` → `PrivacyPolicy`
  - `/terms` → `Terms`
- **`src/App.jsx`** — primarily a slim orchestrator (imports every section component and lays them out in order) that also owns two cross-cutting scroll concerns: restoring the home page's scroll position when arriving back from a legal page (see the dedicated legal-pages entry in Notable Component Behaviors below), and the pre-existing `ScrollTrigger.refresh()` retry timing for GSAP pins. **Refactored out of a single 1,600+ line file** into one-component-per-file under `src/components/` (each section, plus small decorative widgets like `DesignShuffler`/`BuildScanner`/`StrategyScheduler`/`CountUp`/`WorkPreview`/`Field`, all get their own file). Shared data (`SERVICE_ICONS`) lives in `src/constants.js` — the actual copy for those services lives in the translations, not constants.js.
- **`src/pages/PrivacyPolicy.jsx`** / **`src/pages/Terms.jsx`** — standalone static legal pages, same visual shell (logo + "Back to home" link + dated sections), not otherwise linked into the main site's content, and **not translated** (English-only, matching the same choice IntelliAgents made for its own legal pages).

### Section order inside `App.jsx` (top to bottom of the page)

`Navbar` (fixed/floating) → `Hero` → `Features` (3 animated feature cards) → `Pillars` (stat counters) → `Protocol` (sticky stacking 3-step process) → `ServicesGrid` (dark 6-service band) → `Work` (2-project alternating-rows showcase) → `Transformation` (before/after peek carousel) → `Testimonials` (infinite-loop carousel) → `TrustSignals` (3 trust badges) → `ContactForm` → `Footer`.

## Internationalization (English / Bahasa Melayu)

- **`src/translations.js`** — the single source of truth for every piece of user-facing copy on the homepage, nested under `en` and `ms` top-level keys, mirroring each section (`hero`, `features`, `pillars`, `protocol`, `servicesGrid`, `work`, `transformation`, `trust`, `contact`, `footer`, `nav`). **When adding a new section or piece of copy, add it here first** — both languages, kept close in length (not dramatically shorter/longer) so layouts don't visually break between languages.
- **`src/language-context.js`** — just the `LanguageContext` (`createContext`), isolated in its own plain `.js` file.
- **`src/useLanguage.js`** — the `useLanguage()` hook (`{ lang, t, toggleLang }`), also isolated in its own file.
- **`src/i18n.jsx`** — just the `LanguageProvider` component (persists choice to `localStorage` under `sharpable-lang`, sets `document.documentElement.lang`).
- **Why split across four files**: React Fast Refresh's ESLint rule (`react-refresh/only-export-components`) errors if a single file exports both components and non-component values (hooks, contexts, data) together — hence data / context / hook / provider each got their own file rather than living together like IntelliAgents' single `i18n.jsx`.
- **Content-vs-logic separation matters here**: some widgets have data that's partly translatable (text) and partly not (icons, target numbers, tone/color). Pattern used throughout: keep a small local array of the *non-translatable* parts (e.g. `TARGETS` in `Pillars.jsx`, `TONES` in `BuildScanner.jsx`, `IMAGES` in `Protocol.jsx`, `SERVICE_ICONS` in `constants.js`) and `.map()` it together with `t.section.items` at render time — never store translated strings in component state that needs to survive a language switch (see next point).
- **Gotcha already hit once**: don't put translated array items directly into rotating/reorderable `useState` (e.g. a carousel's "current stack order") — when the language toggles, the array reference changes but old state still holds stale-language objects, and syncing via a `useEffect(() => setState(newItems), [items])` trips the `react-hooks/set-state-in-effect` lint rule (and is a real anti-pattern). Fix used in `DesignShuffler.jsx`: store rotation as an array of **indices** (`[0,1,2]`), which are language-independent, and look up `items[idx]` fresh at render time.
- **Toggle UI**: `Navbar.jsx` has the switcher — desktop: `EN / BM` pill button with a `Languages` icon in the main nav row, ported from the IntelliAgents reference project's identical pattern. **Mobile is deliberately different from IntelliAgents**: a compact `EN`/`BM` button sits directly in the top bar immediately left of the hamburger icon (for one-tap access), *not* inside the slide-down menu — it used to be a full-width "Switch to Bahasa Melayu" button inside the mobile menu, moved out on request since burying it in the menu made it slower to reach.

## Notable Component Behaviors

- **`Hero`** — background is **no longer a photo**: it was replaced (2026 polish pass) with `HeroShaderBackground.jsx`, an original WebGL fragment shader (domain-warped fbm flow noise in the site's own dark greys, plus a gold cursor glow that eases toward the pointer each frame — `momentum`-style trailing, not a snap-to-cursor). See the reference-projects list above for why this is original code rather than a port — the visual idea came from a template project, but that template's actual implementation (`shaders`, from shaders.com) needs a paid commercial license this project doesn't hold; **confirmed directly against `shaders.com/license` (v1.7)**, not just the locally-cached copy — its Free Tier explicitly bars exporting or using any output "in a commercial or production context, including client work... or any public-facing deployment," and having gotten the reference via a template doesn't change that. `uMouse`/`uHover` are tracked via a `window`-level `pointermove` listener (not attached to the `<canvas>` itself — the hero's text content sits on top of the canvas in stacking order and would otherwise swallow pointer events before they ever reach it) with a manual bounding-rect check to know when the cursor is over the hero. Respects `prefers-reduced-motion` (renders one static frame instead of a continuous `requestAnimationFrame` loop). **The glow recolors the background rather than shining on top of it**: the first version did `color = base + gold*glow` (additive), which read as "a flashlight" per feedback — the fix computes a *second* palette (the same fbm value `n`, remapped through gold tones instead of grey) and `mix()`es between the two based on the glow mask, so the region near the cursor looks like the flow-noise material itself shifted color, not like a light source was placed over a static image. The mask radius (`smoothstep(0.34, 0.0, dist)`, squared for a sharper edge) was also tightened after "too much spread" feedback — if it ever needs adjusting again, that `0.34` constant is the radius knob. The **old photo background is fully removed** — if a future session ever needs to revert to it, the original monitor-photo `<img>` + gradient-overlay markup is preserved verbatim in the "Original centered Hero" backup block further down this file (same `<img src>`/`brightness-[0.4]` pattern, just under the pre-2026-polish desktop layout — copy only the background `<div>` out of it if the current layout should stay).
  - **Glow palette** (`goldDeep`/`goldMid`/`goldBright` in the fragment shader) is anchored to the site's own tokens (`primary-dark #F0B300` / `primary #FFC629` / `primary-light #FFDD70`, expressed as normalized `vec3`s) rather than an independently-invented ramp — the first version's shadow end (`vec3(0.14, 0.095, 0.02)`) read as "too dark, muddy" against the site's actual yellows, so it was re-anchored to those real tokens (current shadow end: `vec3(0.4, 0.3, 0.03)`). The base grey range was also widened (`greyDeep`/`greyCharcoal`/`greyLight` spread from ~0.05–0.15 to ~0.05–0.32, smoothstep bands steepened) after "increase contrast, make the animated background more noticeable" feedback.
  - **Shape/motion history — worth knowing before trying either again**: two different embellishments were built on top of the plain circular glow and **both were tried and explicitly reverted per feedback**, so don't re-add either without asking first. (1) An organic "morphing blob" edge — the mask distance was perturbed by noise sampled around the angle from the cursor (`atan(toMouse.y, toMouse.x)`) so the boundary slowly wobbled even with the cursor still. Reverted when a comet trail was requested instead ("boring... make it dynamic" led to the wobble; a later ask to add a trail explicitly said to put the *shape* back to a plain circle first). (2) A comet trail — first as `TRAIL_LENGTH=8` discrete stacked circles (`max()` of per-point `smoothstep` masks, decreasing radius/weight going back in the array), then refined into a genuinely continuous ribbon (each pixel's distance to the *nearest point on the segment* between consecutive trail positions, not just the discrete points, tapering `width`/`intensity` by the segment's interpolated position `globalT` along the whole path — verified via `gl.readPixels` on a simulated diagonal trail to confirm the brightness fell off smoothly and monotonically, e.g. `240→158→77→44→36`, not in visible steps). **Explicitly undone per feedback** ("doesn't look very good") back to the original single easing point (`uMouse`, not an array) with no distance perturbation — the current shader has no `uTrail` uniform and no trail/wobble code at all. If asked to revisit either direction again, the git history around the "hero comet trail" / "hero glow rework" commits has both full implementations to start from rather than reinventing them.
  - **Bottom gradient overlay** (the `<div>` sitting on top of `HeroShaderBackground` in `Hero.jsx`) uses an inline `style={{ background: 'linear-gradient(...) }}` with **explicit stop percentages** (`#0F0F12 0%, rgba(15,15,18,0.35) 14%, rgba(15,15,18,0) 38%`) rather than Tailwind's `bg-gradient-to-t from-deep via-deep/25 to-transparent` (which defaults to an even 0/50/100 stop split) — the default split was darkening the shader by the vertical middle of the hero, well before the section's actual bottom edge, per "it fades too early" feedback. Concentrating the fade into roughly the bottom third leaves most of the hero showing the shader clearly. If asked to push it further in either direction, adjust the `14%`/`38%` stop positions directly (the hex/rgba color values don't need to change, just where they land).
  - **Decorative floating-spark dots removed** — three small `animate-float` dots that predated the shader background were dropped once the animated background made them redundant/visually competing.
- **`Logo`** (`src/components/Logo.jsx`) — the real Sharpable wordmark (a white PNG, transparent background, hosted on the `da3lqh4dl` Cloudinary account, natural ratio ≈2.95:1) replacing the earlier gold-circle + `Sparkles`-icon placeholder lockup. Used in `Navbar` (desktop lockup + mobile menu header), `Footer` (brand block), `PrivacyPolicy`, and `Terms` — all as the plain white `<img>` default. A `gold` prop switches to a recolored variant for the Footer's big "Let's make it **Sharpable**" accent heading: instead of an `<img>`, it renders the same PNG as a `mask-image`/`-webkit-mask-image` on a `background-color: currentColor` element, so it inherits whatever `text-*` class is applied (`text-primary` here) — an exact color match with no filter/hue-tuning needed, unlike trying to tint a white image with CSS `filter`. Two real bugs were hit building the current version, both worth knowing if this pattern is reused elsewhere: (1) **a `requestAnimationFrame`-only "never wait forever" safety check is not actually a guarantee** — the polling loop's own deadline was originally checked *inside* the rAF callback itself, so if rAF stops ticking entirely (a backgrounded/hidden tab, hit repeatedly by this exact tool's Browser pane, see the gotcha above — and the same root cause that already forced `Testimonials`' wrap-correction onto `setTimeout` instead of rAF), the deadline check never runs either, and the page stays invisible indefinitely instead of just imperfectly positioned; fixed by adding an independent `setTimeout` backstop that isn't gated behind any rAF tick. (2) **React 18 StrictMode (`main.jsx` wraps everything in `<StrictMode>`) double-invokes effects in dev** — mount → cleanup → mount again, synchronously, before anything is user-visible, specifically to catch missing-cleanup bugs. The first version read `sessionStorage.getItem(HOME_SCROLL_KEY)` **and removed it** as the very first thing the effect did — the throwaway first StrictMode invocation consumed the saved value (and its cleanup correctly cancelled the rest of that invocation's work before it could apply it), so the *second*, real, lasting invocation read back `null` and silently restored to `0` every single time, with no error anywhere. Fixed by moving the read-and-remove *inside* the guarded `finish()` callback, so only whichever invocation actually reaches `finish()` (the cancelled first one never does) touches `sessionStorage` at all. Verified end-to-end (not just "it doesn't crash"): `window.scrollY` after the full round trip matches the saved value exactly, checked across several fresh runs.
