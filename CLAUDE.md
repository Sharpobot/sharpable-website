## Development Commands

Standard Vite project — from the project root:

- `npm install` — install dependencies
- `npm run dev` — start the dev server (Vite default port `5173`, auto-increments to the next free port if occupied — check actual bound port before assuming 5173)
- `npm run build` — production build to `dist/`
- `npm run preview` — preview the production build locally
- `npm run lint` — ESLint (flat config, `eslint.config.js`)

No TypeScript (despite `@types/react`/`@types/react-dom` in devDependencies — those are editor-IntelliSense-only), no test suite, no CI configured yet.

**Dev server dies frequently between turns in this tool environment** (background process gets killed when the session/turn boundary resets) — this is routine, not a bug to chase. Expect to restart it often: check `Get-CimInstance Win32_Process -Filter "Name='node.exe'" | Where-Object { $_.CommandLine -like "*sharpable-website*" }` (PowerShell) before assuming it's still running, restart with `npm run dev` in the background if not, confirm the bound port via `Get-NetTCPConnection`, then open/reconnect the browser preview. **After any `tailwind.config.js` color change specifically**, a plain restart isn't always enough either — hard-navigate the browser tab (not just re-check) before trusting computed colors.

**Stale Tailwind/Vite cache gotcha (hit repeatedly in one session, cost real time each time)**: after editing a component to use a **new arbitrary-value class** that didn't exist anywhere in the codebase before (e.g. `pb-[clamp(4.5rem,16vh,8rem)]`, `-mx-[3rem]`), a plain dev-server restart sometimes serves a stale bundle that's missing the new utility entirely — the class sits correctly in the JSX/DOM, but `getComputedStyle` shows browser defaults (e.g. `position: relative` instead of `sticky`, `margin-top: 0px` instead of the intended negative value) as if the class were never generated. This reads exactly like a real positioning bug and is easy to chase down the wrong path. **Fix**: `rm -rf node_modules/.vite` before restarting (`Stop-Process` the node process first, delete the cache dir, then `npm run dev` again) — this forces Tailwind/Vite to fully re-scan and re-bundle rather than reuse a cache that predates the new class. **Always verify** any brand-new arbitrary-value class actually compiled (check `getComputedStyle` in the browser) before concluding a positioning/sizing bug is a real logic error rather than this cache issue — this exact false alarm happened more than once.

**Programmatic scroll doesn't reliably fire native events in this tool's Browser pane** — `window.scrollTo()`/`scrollBy()`/`Element.scrollIntoView()` move the actual scroll position but frequently don't dispatch the `'scroll'` event, don't run `requestAnimationFrame` callbacks reliably, and don't trigger `position: sticky` re-resolution — all things a real user's scroll input does automatically. This makes JS-driven scroll simulation useless for verifying anything scroll-linked (GSAP ScrollTrigger, the Testimonials carousel's wrap logic, ServicesGrid's mobile journey spine, any `position: sticky` element). **What actually works**: a real simulated gesture via the `computer` tool's `scroll` action (max `scroll_amount: 10` per call, batch several via `browser_batch` to cover distance), then `computer{action:"screenshot"}` to confirm visually — or `computer{action:"scroll_to", ref: "..."}` using a ref from `read_page`/`find` to jump to a specific element reliably (far more precise than blind pixel-scrolling or the broken `scrollIntoView`). Also worth knowing: the Browser pane sometimes reports itself as not compositing frames at all (`document.hidden === true`, screenshots time out, `requestAnimationFrame` never fires) for stretches of a session for reasons outside this tool's control — retry later in the same session rather than assuming a fix is needed; when it's confirmed hidden, fall back to direct DOM/computed-style assertions instead of visual checks, and say so explicitly rather than claiming a visual check happened when it didn't. The `computer` tool's own `scroll` action can also silently no-op (reports success, `window.scrollY` never moves) for stretches of a session unrelated to the `document.hidden` issue — if a real gesture doesn't move `scrollY` after a couple of tries, fall back to `window.scrollTo({top, behavior:'instant'})` + a manual `window.dispatchEvent(new Event('scroll'))` (the dispatch is what actually invokes `addEventListener('scroll', ...)` handlers; `scrollTo` alone won't), then wait ~1s for GSAP/`scroll-behavior:smooth` to settle before reading state back.

**This applies to canvas/WebGL animations too, not just scroll-linked CSS** — a `requestAnimationFrame` loop driving a `<canvas>` (e.g. `HeroShaderBackground.jsx`) is just as stuck as everything else while `document.hidden === true`, so a screenshot taken then will show a frozen frame with no live mouse-reactivity even though the code is correct. **A more rigorous check that doesn't depend on rAF or `document.hidden` at all**: grab the same canvas's WebGL context again from outside the component (`canvas.getContext('webgl')` returns the *same* context, not a new one), read back `gl.getParameter(gl.CURRENT_PROGRAM)` to get the already-linked program, look up its uniform locations again by name, force-set them to specific test values, call `gl.drawArrays(...)`, then `gl.readPixels(...)` *immediately* in that same synchronous call — this bypasses the browser's own frame scheduling entirely and proves the shader math is correct (e.g. compare the same pixel with a `uHover` uniform forced to `0` vs `1` and diff the RGB output) even when a live on-screen check is blocked. For verifying a *trail*/*path* effect specifically (not just a single point), simulate a synthetic multi-point path and check that the readback brightness changes *smoothly and monotonically* along it, not just that the endpoints look right — this is what caught the difference between the discrete-blob trail and the continuous-ribbon one during the `HeroShaderBackground` trail work (later reverted; see the `Hero` entry below).

**`read_console_messages` can return a stale/cached error from a *previous* failed HMR update, not the current page state** — hit while iterating on `HeroShaderBackground.jsx`: after fixing a `ReferenceError` (a leftover reference to a since-removed constant), the tool kept reporting the exact same error with the exact same timestamp across multiple fresh navigations and even a full dev-server restart, while the component was actually compiling and running correctly the whole time (confirmed via `gl.getParameter(gl.CURRENT_PROGRAM)` returning a valid linked program with `gl.getError()` returning `0`). **Don't trust a console error at face value if you've since fixed the code it points to** — re-verify via the actual runtime behavior (a WebGL readback, a computed style, a DOM query) rather than assuming the bug is still live just because the log line is still there.

**`window.scrollTo(x, y)` (the legacy 2-argument form) is equivalent to `behavior: 'auto'`, which defers to whatever `scroll-behavior` the target element has** — this project sets `html { scroll-behavior: smooth }` globally (`index.css`), so any "instant jump to a position" call written as the 2-arg form actually *animates* there over a couple hundred ms instead of snapping. This was a real, user-visible bug (legal pages "scrolling up briefly" instead of opening already at the top) that survived an earlier fix that only addressed the *timing* (moving the effect from `useEffect` to `useLayoutEffect`) without addressing this. **Whenever an instant, non-animated scroll position is actually intended, always use the explicit object form with `behavior: 'instant'`** — `window.scrollTo({ top, left, behavior: 'instant' })` — never the bare 2-arg form, anywhere in this codebase.

**React 18 `<StrictMode>` (this project wraps everything in it, `main.jsx`) double-invokes effects in dev** — mount → cleanup → mount again, synchronously, before the user sees anything, specifically to help catch missing-cleanup bugs. This is invisible for most effects, but **an effect that destructively reads-and-clears external state (e.g. `sessionStorage.getItem(...)` immediately followed by `removeItem(...)`) as its first action will have that first, throwaway StrictMode invocation consume the value before the second, real, lasting invocation ever runs** — silently breaking the feature with no error anywhere (hit in `App.jsx`'s scroll-restoration effect; see the legal-pages entry below for the full story). If an effect needs to destructively consume something, defer the read-and-clear until the exact moment the value is actually used/applied (e.g. inside a guarded callback only one invocation can reach), not as the effect's first line.

## High-Level Architecture

- **`src/main.jsx`** — entry point. Wraps everything in `LanguageProvider` (i18n context, see below) then `BrowserRouter` with three routes:
  - `/` → `App` (the entire one-page marketing site)
  - `/privacy` → `PrivacyPolicy`
  - `/terms` → `Terms`
- **`src/App.jsx`** — primarily a slim orchestrator (imports every section component and lays them out in order) that also owns two cross-cutting scroll concerns: restoring the home page's scroll position when arriving back from a legal page (see the dedicated legal-pages entry in Notable Component Behaviors below), and the pre-existing `ScrollTrigger.refresh()` retry timing for GSAP pins. **Refactored out of a single 1,600+ line file** into one-component-per-file under `src/components/` (each section, plus small decorative widgets like `DesignShuffler`/`BuildScanner`/`StrategyScheduler`/`CountUp`/`WorkPreview`/`Field`, all get their own file). Shared data (`SERVICE_ICONS`) lives in `src/constants.js` — the actual copy for those services lives in the translations, not constants.js.
  - **Everything below `Hero` is lazy-loaded** (`Features` through `Footer`, via `React.lazy` + two `<Suspense fallback={null}>` boundaries — one wrapping the below-Hero sections inside `<main>`, a separate one around `Footer`) — a real performance pass, not just a refactor: the main JS chunk dropped from 447KB to 378KB (130.6KB gzip) since none of that code has to parse/execute before the page is interactive. `Navbar` and `Hero` stay eager imports and sit **outside** any Suspense boundary — Hero fills the entire first viewport (`min-h-[100dvh]`), so nothing below it is ever visible without scrolling first, and critically, if Hero were *inside* the same Suspense boundary as the lazy sections it would wait on all of them too (a Suspense boundary blocks its whole subtree together, not per-child) — exactly the outcome this change is trying to avoid. The pre-existing `ScrollTrigger.refresh()` calls (200ms/1000ms/`window.load`) already re-measure pin/scrub ranges once the real page height is known, which turned out to be exactly the mechanism a late-mounting lazy section also needs — no separate handling was required for that.
- **`src/pages/PrivacyPolicy.jsx`** / **`src/pages/Terms.jsx`** — standalone static legal pages, same visual shell (logo + "Back to home" link + dated sections), not otherwise linked into the main site's content, and **not translated** (English-only, matching the same choice IntelliAgents made for its own legal pages).

### Section order inside `App.jsx` (top to bottom of the page)

`Navbar` (fixed/floating) → `Hero` → `Features` (3 animated feature cards) → `Pillars` (stat counters) → `Protocol` (sticky stacking 3-step process) → `ServicesGrid` (dark 6-service band) → `Work` (2-project alternating-rows showcase) → `Transformation` (before/after peek carousel) → `Testimonials` (infinite-loop carousel) → `TrustSignals` (3 trust badges) → `ContactForm` → `Footer`.

## Internationalization (English / Bahasa Melayu)

- **`src/translations.js`** — the single source of truth for every piece of user-facing copy on the homepage, nested under `en` and `ms` top-level keys, mirroring each section (`hero`, `features`, `pillars`, `protocol`, `servicesGrid`, `work`, `transformation`, `trust`, `contact`, `footer`, `nav`). **When adding a new section or piece of copy, add it here first** — both languages, kept close in length (not dramatically shorter/longer) so layouts don't visually break between languages.
- **`src/language-context.js`** — just the `LanguageContext` (`createContext`), isolated in its own plain `.js` file.
- **`src/useLanguage.js`** — the `useLanguage()` hook (`{ lang, t, toggleLang }`), also isolated in its own file.
- **`src/i18n.jsx`** — just the `LanguageProvider` component (persists choice to `localStorage` under `sharpable-lang`, sets `document.documentElement.lang`).
- **Why split across four files**: React Fast Refresh's ESLint rule (`react-refresh/only-export-components`) errors if a single file exports both components and non-component values (hooks, contexts, data) together — hence data / context / hook / provider each got their own file rather than living together like IntelliAgents' single `i18n.jsx`.
- **Content-vs-logic separation matters here**: some widgets have data that's partly translatable (text) and partly not (icons, target numbers, tone/color). Pattern used throughout: keep a small local array of the *non-translatable* parts (e.g. `TARGETS` in `Pillars.jsx`, `TONES` in `BuildScanner.jsx`, `IMAGES` in `Protocol.jsx`, `SERVICE_ICONS` in `constants.js`) and `.map()` it together with `t.section.items` at render time — never store translated strings in component state that needs to survive a language switch (see next point).
- **Gotcha already hit once**: don't put translated array items directly into rotating/reorderable `useState` (e.g. a carousel's "current stack order") — when the language toggles, the array reference changes but old state still holds stale-language objects, and syncing via a `useEffect(() => setState(newItems), [items])` trips the `react-hooks/set-state-in-effect` lint rule (and is a real anti-pattern). Fix used in `DesignShuffler.jsx`: store rotation as an array of **indices** (`[0,1,2]`), which are language-independent, and look up `items[idx]` fresh at render time.
- **Toggle UI**: `Navbar.jsx` has the switcher — desktop: `EN / BM` pill button with a `Languages` icon in the main nav row, ported from the IntelliAgents reference project's identical pattern. **Mobile is deliberately different from IntelliAgents**: a compact `EN`/`BM` button sits directly in the top bar immediately left of the hamburger icon (for one-tap access), *not* inside the slide-down menu — it used to be a full-width "Switch to Bahasa Melayu" button inside the mobile menu, moved out on request since burying it in the menu made it slower to reach.

```js
primary-dark: '#F0B300'   // secondary/supporting-text tier of the same accent
primary-light: '#FFDD70'

```

**These values have moved several times already this project** — originally a much darker/near-black, near-muted-gold palette; lightened + made more vibrant on request; background pulled back darker after "too light" feedback while *keeping* the more vibrant gold; `primary-dark` brightened once more (`#D69600` → `#F0B300`) after it read as "muddy" next to the brighter accent spans. **`primary-dark`'s role is deliberate, not a mistake to "fix" by matching it to `primary`**: it's the secondary/supporting tier (eyebrow labels, tag pills, feature-card sub-lines, protocol taglines) versus `primary` for headline accents/CTAs/buttons — that two-tier split is real visual hierarchy. If it ever looks inconsistent again, first check it's genuinely inconsistent (grep `text-primary-dark` across `src/components/` — as of this writing it's already 100% one token, no drift) before assuming it needs unifying with `primary`. **If asked to touch these values again**: (1) update `tailwind.config.js` first — that's the single source of truth; (2) then grep for hardcoded hex/rgba duplicates of the old values in `src/index.css` (`::selection`, scrollbar, `.glass`/`.glass-dark`, `.gradient-text`, `.grid-bg`, `.ring-pulse`) and inline in `BuildScanner.jsx`/`DesignShuffler.jsx` (SVG fills/JS color logic can't use Tailwind classes) — these do **not** update automatically, `sed -i 's/#OLDHEX/#NEWHEX/g'` across those files is the fast way; (3) **a plain HMR update is not enough for Tailwind config color changes** — kill and restart the dev server, then hard-navigate the browser tab, or you'll keep reading stale computed colors and think the edit didn't take effect (this has happened repeatedly in this project — always verify via `getComputedStyle(...).color` in the browser after a config color change, never trust that the edit alone was sufficient).

**Scrollbar** (`src/index.css`, `::-webkit-scrollbar*`): deliberately swapped from a thick 10px rounded-pill scrollbar to a slim 3px bar with a 2px radius and no hover-darken, matching an older Sharpable site's minimal scrollbar look — colors still come from this project's own tokens (`background`/`primary`), not the old site's.

**Fonts** (self-hosted via `@fontsource`, imported in `main.jsx` — **not** Google Fonts anymore; that `<link>` in `index.html` is gone):
- `font-display` → **Archivo Variable, semi-expanded** — headings. **Swapped from Plus Jakarta Sans** to match the new logo's wordmark (set in Archivo SemiExpanded). Archivo has no separately-published "SemiExpanded" family — width is a variable axis on the one family. So it's `@fontsource-variable/archivo/wdth.css` (imported in `main.jsx`; its `@font-face` family name is literally `'Archivo Variable'`, which is what `tailwind.config.js`'s `fontFamily.display` references and what DevTools shows) **plus** `.font-display { font-stretch: semi-expanded; }` in `src/index.css` (computes to `112.5%`). Seeing "Archivo Variable" in DevTools rather than "SemiExpanded" is expected — check the `font-stretch` line instead. One variable file (~90KB latin) covers every weight 100–900 and width 62–125%, so `font-semibold/bold/extrabold` on headings need no per-weight imports anymore. Fontsource ships no pre-split latin-only CSS for variable builds, so `wdth.css` declares vietnamese/latin-ext/latin subsets, but the browser only ever fetches the latin file (verified via network log) — `unicode-range` gating makes the combined import free. The old `@fontsource/plus-jakarta-sans` package was uninstalled. If the heading font ever changes again: swap the import in `main.jsx`, the `display` family name in `tailwind.config.js`, and the `.font-display` rule in `index.css` — those three places only.
- `font-serif` → **Cormorant Garamond**, always used *italic* — the recurring accent phrase at the end of headings (e.g. "…look **big.**", "Let's make it **Sharpable.**")
- `font-body` → **Inter** — body copy
- `font-mono` → **JetBrains Mono** — uppercase letter-spaced eyebrows/labels/badges throughout

**Self-hosting switch (a later session; note the Plus Jakarta Sans weights below are historical — that font was later replaced by Archivo, see above)**: a real Lighthouse run flagged the Google Fonts `<link>` as the single biggest render-blocking cost on the page (778ms of a 1,800ms total, just for the round trip to fetch its CSS before any font file could even be requested — `font-display: swap` avoids invisible text but not that extra hop). Fixed by auditing every `font-*` weight class actually used anywhere in the codebase and self-hosting only those: Plus Jakarta Sans 600/700/800 only (400/500 were requested but never used), Cormorant Garamond *italic* 400/500 only (every upright variant plus italic 600 were dead weight — matches the "always used italic" note above), Inter 400/500/600 only (300/700 unused), JetBrains Mono 400 only (500/600 never have a weight override anywhere). Imported via `@fontsource`'s `latin-*` subset files specifically (`import '@fontsource/inter/latin-500.css'` etc., in `main.jsx`) rather than the combined per-weight files, which would otherwise bundle cyrillic/greek/vietnamese `@font-face` declarations this English/Bahasa-Melayu site never needs. Real result: FCP 3.5s→2.7s, LCP 4.1s→3.2s. If a new weight is ever needed for a new heading/component, add the matching `@fontsource/<family>/latin-<weight>[-italic].css` import to `main.jsx` — don't add it back to a Google Fonts `<link>`.

**Signature typographic motif**: nearly every section heading pairs a bold sans-serif line with an italic serif accent line in `primary` (the bright gold — all such accent spans were unified onto `primary` rather than a mix of `primary`/`primary-dark`, on request, for visual consistency). This pattern repeats in Hero, Features, Pillars, Protocol, ServicesGrid, Work, Transformation, ContactForm, and Footer — treat it as the site's core visual identity, not a one-off. These accent spans also got deliberately enlarged beyond their parent heading's size (e.g. `text-4xl sm:text-5xl md:text-6xl` heading with a `text-5xl sm:text-6xl md:text-7xl` accent span) — keep new headings proportionate to this if you add one.

**Corner radius scale — the "unround" pass (this replaced the old very-rounded look; read this before touching any `rounded-*` class)**: the site originally used very large radii (8px–64px, pill-shaped buttons everywhere), which felt off-brand for "Sharpable". It was compressed into a subtle, graduated **4.5px–12px** band, tuned over three rounds of live feedback (6–16px first → 3–8px "even sharper" → the exact midpoint of those two, 4.5–12px, which the user picked after comparing all three live; the git history has each variant if one is ever wanted back). The scale lives in **one place**, `tailwind.config.js` → `theme.extend.borderRadius`, overriding both the custom tiers and the stock Tailwind ones:
`lg` 0.28125rem (4.5px) · `xl` 0.375rem (6px) · `2xl` 0.46875rem (7.5px) · `3xl` 0.5625rem (9px) · `2.5xl` 0.5625rem · `4xl`/`5xl` 0.65625rem (10.5px) · `6xl`/`7xl` 0.75rem (12px). Cards, inputs, containers, images all use these tokens, so retuning the whole site's roundness is a one-file edit.
- **`rounded-full` is deliberately NOT overridden** — it's still correct (and used) for real circles: avatars, status dots, icon-only buttons (hamburger, close ×, remove ×, lightbox close, carousel arrows, drag handle), success-icon circle, blur-glow blobs, and thin progress/slider-dot bars. Overriding `full` would have broken every genuine circle.
- **Wide pill-shaped buttons and text badges** that used `rounded-full` for a stadium shape (all CTA buttons, tag pills, the language toggle, the Transformation before/after labels) were changed to **`rounded-lg`** in their own component files — so they track the shared `lg` token and retune automatically with the scale. **Convention going forward: a wide/text button or badge = `rounded-lg`; only a square icon-only control or a dot = `rounded-full`.**
- **Navbar uses explicit pixel values, not tokens** (`rounded-[7.5px]`, both the `lg:` desktop pill and the mobile unscrolled bar — the same value so they match; mobile *scrolled* stays `rounded-none` because it's a deliberate full-bleed bar). If the scale is retuned, update these two by hand (they're the tier-`2xl` value). **`BuildScanner`'s decorative SVG `rx` attributes** (`1.5` / `1.1`, the fake browser-chrome bar) also can't use Tailwind classes and were retuned by hand.
- `ServicesGrid`'s `rounded-[2px]` diamond notches and the 2px scrollbar thumb were already sharp and untouched.
- After adding any *new* arbitrary radius like `rounded-[7.5px]`, do the `rm -rf node_modules/.vite` + restart described in Development Commands — this exact class hit the stale-cache gotcha again during this pass.

**Custom utility classes** (`src/index.css`, `@layer components`):

Two real bugs were found by reading the code and **reproduced live** before fixing, plus one hardening:
  - **Permanent freeze after scrolling the hero out of view and back.** `render()` only re-scheduled itself `if (!reducedMotion && visible)`, but never reset `rafId` to `null` when it *stopped*, so `rafId` kept a stale, already-fired id. To make that possible, all GL resource creation (shaders, program, buffer, uniform locations) was extracted into a `setupGL()` function that fills a mutable `uniforms` object; `render()` reads `uniforms.uResolution` etc. Both handlers are removed in the effect cleanup. - **Loading screen** (`src/components/LoadingScreen.jsx`, wired into `App.jsx`) — a small centered progress track + percentage readout (no logo/wordmark — deliberately removed on request: "not obnoxious... much smaller and more subtle") shown while the page is genuinely still loading, researched before building (see the "Loading State Concepts" and "Live Counter Loading" Artifacts referenced in Known Gaps below for the research this came from and the rejected alternatives — a fixed-duration counter and cycling loading text were both explicitly considered and rejected as the "manufactured" anti-pattern).
  - **How it works**: the percentage is never a fixed timeline. It eases toward a 92% ceiling (`CEILING_PCT`) over `EASE_DURATION_MS` (900ms) while genuinely still waiting, then only completes the remaining distance to 100% once real readiness flips true (`FINISH_DURATION_MS`, 220ms), holds at 100% briefly (`HOLD_MS`, 200ms) so it registers rather than flashing, then fades out (`FADE_MS`, 350ms) and unmounts. It also never shows anything at all for a wait shorter than `SHOW_DELAY_MS` (180ms) — per the research, an indicator for a sub-~200ms wait is noise, not information, so on a fast load (or a repeat visit with everything cached) the page just appears with no loader at all, same as before this existed.
  - **What "readiness" actually means here — read this before changing what it's tied to**: it is the AND of two genuinely different signals, not one. `App.jsx`'s own `ready` state (passed in as `appReady`) is **not** a general "the page has visually loaded" flag — it's narrowly scoped to the scroll-restore case (coming back from `/privacy` or `/terms` via "Back to home") and is already `true` from the very first render on a normal first visit, since there's nothing to restore. This was hit as a real bug while building this: using `appReady` alone meant the loading screen never showed at all for a normal first visit — the exact case it's meant for — because that flag was already `true` before the loader's own `SHOW_DELAY_MS` timer ever fired. Fixed by combining it with the browser's own `document.readyState`/`load` event (`pageLoaded` state inside `LoadingScreen`), which is what actually waits for fonts, stylesheets, and every eagerly-loaded image to finish. `trulyReady = pageLoaded && appReady` is the real signal driving everything.
  - **Verifying this locally is deceptive**: on the Vite dev server, `window.load` fires around ~80ms after navigation (confirmed via `performance.getEntriesByType('navigation')[0].loadEventEnd`) — genuinely too fast to ever need the loader, so on `localhost` it will almost always skip straight to the fast path, which is *correct* behavior, not a bug. To verify the visible-loader code path, temporarily override `pageLoaded`'s initial `useState` to `false` and replace the real `load`-event effect with a `setTimeout` (simulating a slow load), and multiply the timing constants by a large factor (e.g. `* 20`) so the whole sequence is comfortably catchable across separate tool round-trips — revert both overrides afterward. This is how the sequencing below was actually confirmed, not assumed.
  - **The timing-bug fix this was built alongside**: `Hero.jsx`'s entrance animation (`.hero-line-1`/`.hero-line-2`/`.hero-cta`/`.hero-meta` GSAP tweens) used to fire unconditionally on mount via a plain `useEffect(() => {...}, [])` — unlike every other section's reveal, which is gated behind `ScrollTrigger`'s `start: 'top 90%', once: true` and therefore naturally can't fire until the user actually scrolls there. Hero is above the fold, so nothing gated it, and since the whole page tree sits `visibility: hidden` until `App.jsx`'s `ready` flips (a *separate* concern from the loading screen — see the scroll-restore entry below), that ~1.6s entrance was very likely finishing completely unseen, behind the hidden page, before anyone ever saw it — loading screen or not. Fixed by threading a new `canAnimate` flag from `App.jsx` (flips true only via `LoadingScreen`'s `onDone` callback — which fires once, whether or not the loader ever actually became visible) down to `Hero`, which now gates its GSAP context on it (`useEffect(() => { if (!canAnimate) return; ... }, [canAnimate])`). **Verified with real timestamps, not just visually** (screenshots are too slow relative to real timings to catch this any other way): a temporary `window.__loadingScreenDoneAt`/`window.__heroAnimStartAt` pair (set at the `resolve()` call and at the top of Hero's gated effect, removed after confirming) showed the animation starting ~49ms after the loader resolved — sequential, not overlapping or pre-empting.
  - **"Load → cover → reveal" stutter fix (first observed on the real deploy; never visible on localhost)**: on a real Netlify load the user saw the site flash, then a loading overlay hard-pop in on top, then the same site revealed again. Root cause (traced in code, then reproduced by temporarily forcing `pageLoaded` false + a delayed setTimeout): `App.jsx`'s wrapper `visibility` was tied only to `ready`, which is `true` from the first render on a normal visit (it only exists for the scroll-restore case). So the real page painted immediately while `LoadingScreen` — gated on the slower `window.load` — waited its 180ms `SHOW_DELAY_MS`, *then* mounted an opaque overlay (no fade-**in**, only fade-out) over already-visible content. 'visible' : 'hidden'`** — `canAnimate` only flips when `LoadingScreen` resolves (immediately if it never showed; after its fade-out if it did), so nothing is visible before the exact moment the loader is gone. The current approach: `App`'s `ready` state starts `false` whenever a saved position exists (decided synchronously in the `useState` initializer, *before* the first render, so the hidden state genuinely prevents a flash rather than just shortening one) and the whole page tree renders with `style={{ visibility: ready ? 'visible' : 'hidden' }}` — reserving layout, painting nothing — until a `useLayoutEffect` polls `document.body.scrollHeight` across animation frames and finds it unchanged for 3 consecutive ticks (or a 700ms hard deadline passes), at which point it sets `scrollY` and flips `ready` to `true` **in the same step**, so the very first thing the user sees is the page already correctly positioned. This replaced an earlier version that retried a `scrollTo` on a `setTimeout(200)`/`setTimeout(1000)` schedule and re-applied the position each time — that version *worked* (eventually landed on the right spot) but was visibly a "jump to top, wait, jump to the real spot" sequence, because every retry happened after the page had already painted somewhere wrong. Two real bugs were hit building the current version, both worth knowing if this pattern is reused elsewhere: (1) **a `requestAnimationFrame`-only "never wait forever" safety check is not actually a guarantee** — the polling loop's own deadline was originally checked *inside* the rAF callback itself, so if rAF stops ticking entirely (a backgrounded/hidden tab, hit repeatedly by this exact tool's Browser pane, see the gotcha above — and the same root cause that already forced `Testimonials`' wrap-correction onto `setTimeout` instead of rAF), the deadline check never runs either, and the page stays invisible indefinitely instead of just imperfectly positioned; fixed by adding an independent `setTimeout` backstop that isn't gated behind any rAF tick. (2) **React 18 StrictMode (`main.jsx` wraps everything in `<StrictMode>`) double-invokes effects in dev** — mount → cleanup → mount again, synchronously, before anything is user-visible, specifically to catch missing-cleanup bugs. The first version read `sessionStorage.getItem(HOME_SCROLL_KEY)` **and removed it** as the very first thing the effect did — the throwaway first StrictMode invocation consumed the saved value (and its cleanup correctly cancelled the rest of that invocation's work before it could apply it), so the *second*, real, lasting invocation read back `null` and silently restored to `0` every single time, with no error anywhere. Fixed by moving the read-and-remove *inside* the guarded `finish()` callback, so only whichever invocation actually reaches `finish()` (the cancelled first one never does) touches `sessionStorage` at all. Verified end-to-end (not just "it doesn't crash"): `window.scrollY` after the full round trip matches the saved value exactly, checked across several fresh runs.
